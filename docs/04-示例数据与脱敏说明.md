# 04 · 示例数据与脱敏说明

本仓库为公开项目，**不包含任何真实设备、产线或客户的现场信息**。
这份文档说明：示例数据是怎么来的、做了哪些替换、以及你换成自己工程时该改哪里。

---

## 1. 示例工程 `DEMO_MACHINE` 是合成的

`example/DEMO_MACHINE.Device.Application.xml` 由脚本生成，不是从任何真实 PLC 导出的：

```bash
python tools/make-demo-xml.py
```

生成结果：

```
[v] example/DEMO_MACHINE.Device.Application.xml
    类型 14 简单 + 2 枚举 + 9 数组 + 7 结构体；符号 44 个（5 个 GVL）
    注意：本文件为纯合成演示工程，不对应任何真实设备。
```

它按 CODESYS「符号配置」导出的真实格式编写，因此解析、生成、握手、读写
**走的都是与真实工程完全相同的代码路径**——只是名字通用化。

### 为什么要合成而不是裁剪真实 XML

真实符号配置里的信息密度很高，删掉名字也没用：

| 信息类型 | 例子 | 为什么敏感 |
|---|---|---|
| GVL 分层结构 | 全局层 / 工位层 / 手册层 | 暴露设备工艺划分 |
| 结构体成员与偏移 | 轴控制数据、状态字、参数组 | 暴露控制逻辑与硬件配置 |
| 数组维度与语义 | 报警/提示/故障三个码表 | 暴露报警体系设计 |
| 中文注释 | `产量计数`、`流程字`、`气压正常` | 直接说明产线在做什么 |
| 类型尺寸异常 | 某结构体声明 1B 实占 8B | 暴露厂商库实现细节 |

只替换变量名而保留结构，等于把工艺图纸的编号换掉、线条保留。
所以整份 XML 用通用命名重新合成。

## 2. 演示工程覆盖了哪些结构

真实工程里出现过的每一种「会让代码走不同分支」的形态，演示工程里都有等价物，
否则脱敏就会把功能验证一并删掉。

| 形态 | 演示工程里的实例 | 用来验证 |
|---|---|---|
| IEC 标量 | 14 种基础类型（BOOL…LREAL/STRING） | 编解码宽度 |
| 一维数组 | `aAlarmFlag ARRAY[0..100] OF BOOL` | 元素按名寻址 |
| 非 0 起始下标 | `aStationNo ARRAY[1..6] OF DINT` | 下标范围校验 |
| 结构体 | `ST_PANEL_IN` / `ST_PANEL_OUT` | 成员读写 |
| 结构体数组 | `aAxisCtl ARRAY[0..7] OF ST_AXIS_CONTROL` | 元素 + 成员多层路径 |
| 嵌套结构体 | `aAxisCtl[3].tState.bValid` | 任意深度寻址 |
| 结构体内数组 | `aAxisCtl[3].aAbsSel[1]` | 组内数组元素 |
| 枚举 | `E_MODE` / `E_PRODUCT_RESULT` | 字面量名显示 |
| UNION | `aCell[n].uResult`（`eResult` 与 `di` 叠在偏移 0） | 布局对账 |
| 布局可疑结构 | `ST_CELL` 声明 size=1 实占 8B | 整读/逐名读对账 |
| 数组步长不可信 | `aCell ARRAY[1..6] OF ST_CELL` 声明 6B 实占 72B | 从整读长度反推步长 |

最后三种是刻意保留的「坑」：真实工程里正是它们让整读解码出错，
删掉就等于删掉了最有价值的那部分验证。它们在演示工程里同样不可信，
但**不指向任何真实设备**。

## 3. 命名规则（不列原名称）

> 这一节刻意**不提供「原名 → 新名」对照表**——列出原名就等于没脱敏。
> 这里只说明新名字遵循的规则，方便你读懂示例工程。

演示工程的命名遵循两条规则：

**GVL 按职责划分，前缀统一 `GVL_`**

| GVL | 职责 |
|---|---|
| `GVL_MAIN` | 主逻辑全局量：计数、运行状态、报警/提示/故障三组码表、工位号表 |
| `GVL_AXIS` | 轴相关：控制数据结构体数组、参数结构体数组 |
| `GVL_STATION` | 工位参数与测量值、工位数据数组（含联合体） |
| `GVL_IO` | IO 与安全信号、面板输入输出结构体 |

**变量用匈牙利前缀 + 英文语义**

| 前缀 | 类型 |
|---|---|
| `b` | BOOL（`bRunning`、`bSafetyDoor`） |
| `i` / `di` | INT / DINT（`iMode`、`diTotalCount`） |
| `f` / `lr` | REAL / LREAL（`fSetPosition`、`lrSpeed`） |
| `r` | REAL 且语义为「实测/设定值」（`rActual`、`rUpperLimit`） |
| `a` | 数组（`aAlarmFlag`、`aAxisCtl`） |
| `st` | 结构体实例（`stInput`、`stOutput`） |
| `e` | 枚举（`eMode`） |

**类型名统一 `ST_` / `E_` / `U_` 前缀**

| 前缀 | 含义 |
|---|---|
| `ST_` | 结构体（`ST_AXIS_CONTROL`、`ST_PANEL_IN`） |
| `E_` | 枚举（`E_MODE`、`E_PRODUCT_RESULT`） |
| `U_` | 联合体（`U_CELL_RESULT`） |

**注释只保留通用工业词汇**（总计数、运行中、上限设定、气压正常…），
不含设备型号、产品名、工位工艺描述或客户信息。

## 4. 网络地址一律用文档保留段

代码与文档中的 IP 全部为 **RFC 5737 文档保留地址**，不会指向任何真实主机：

| 用途 | 值 |
|---|---|
| 默认 PLC 地址 | `192.0.2.10` |
| 不可达示例 | `192.0.2.250` |
| 源网卡示例 | `192.0.2.36` |

`192.0.2.0/24`（TEST-NET-1）是 IANA 专为文档与示例保留的网段。
把它当默认值的好处：即使有人忘了改地址直接运行，也不会连到别人的设备上。

端口 `11740` 是 CODESYS `CmpIecVarAccess` 的行业固定端口，属于协议常量，
不是现场信息，因此保留。

## 5. 清除了哪些「实测痕迹」

原文档里有一些来自真实调试的观测值，已全部删除或改为占位：

| 原内容 | 现在 |
|---|---|
| 具体会话号/句柄/令牌 | `<8 位十六进制>` 等占位，每台 PLC 每次连接都不同 |
| 具体读数值 | `<当前值>` |
| 具体耗时 | `<耗时 ms>` |
| 审计报告里写死的「可读 N/N、最大 N B」 | 改为按 XML 计算的 `可写符号 N` |
| 设备型号与产线名 | 删除 |

> 会话号、块号、设备令牌本来就是每次连接随机的，写进文档既无参考价值，又会让人误以为是固定值。

## 6. 换成你自己的工程

脱敏只影响示例数据，工具链一行没改。三步替换：

```bash
# ① 把自己的符号配置 XML 放进 example/（或 Test/）
cp 你的程序.Device.Application.xml example/

# ② 生成（会把 example/ 与 Test/ 下的 XML 全部处理）
python tools/gen_tags.py --all

# ③ 启动时指定你的程序名
2-run-verify.bat 你的程序名
```

如果工具链认不出你的程序，会提示「与内置模板完全不匹配——自动选点」，
此时先自动选前 32 个标量让界面能起来，再编辑
`server/profiles/<你的程序>.profile.json` 精确选点后重跑第 ② 步。

写入前记得改白名单（`server/write-whitelist.json`）——默认只放行演示工程的设定值，
换程序后那些条目会被自动过滤掉，等于「全禁写」，这是安全的默认行为。

## 7. 提交前自查（给后续维护者）

改完代码或文档、准备推公开仓库前跑这几条。下面用 `<旧前缀>` 之类占位符表示
**你自己历史工程里的命名特征**——这类关键词不要写进仓库，否则检查清单本身就成了线索。

```bash
# ① 真实网段（应无输出）
grep -rn "192\.168\.\|172\.16\.\|10\.[0-9]\+\.[0-9]\+\.[0-9]\+" \
     --include="*.js" --include="*.json" --include="*.md" --include="*.html" \
     --include="*.py" --include="*.bat" --include="*.xml" . | grep -v node_modules

# ② 历史工程命名（应无输出；把 <旧前缀> 换成自己的）
grep -rniE "<旧GVL前缀>|<旧类型前缀>|<设备型号>|<产线中文名>" \
     --include="*.md" --include="*.js" --include="*.json" --include="*.py" . \
     | grep -v node_modules

# ③ 文档里的变量路径是否真的存在于示例工程（应输出 [v]）
python - <<'EOF'
import json, re, pathlib, sys
sys.stdout.reconfigure(encoding='utf-8')
tab = json.load(open('out/DEMO_MACHINE/tag_table.json', encoding='utf-8'))
syms = {s['symbolPath'].replace('Application.', '') for s in tab['symbols']}
bad = []
for f in ['README.md', 'docs/01-协议手册.md', 'docs/02-源码手册.md', 'docs/03-复现流程.md']:
    s = pathlib.Path(f).read_text(encoding='utf-8')
    for m in re.finditer(r'\b(GVL_[A-Z]+)((?:\.\w+|\[\d+\])+)', s):
        full = m.group(1) + m.group(2)
        base = full.split('[')[0].split('.')
        if not any('.'.join(base[:i]) in syms for i in range(len(base), 0, -1)):
            bad.append((f, full))
print('[v] 文档变量路径全部有效' if not bad else bad)
EOF
```

三条各自防的是不同的事：

| 检查 | 防什么 |
|---|---|
| ① | 默认值或示例里残留内网地址 |
| ② | 复制粘贴旧工程的代码片段与注释 |
| ③ | 改了示例工程结构后，文档示例路径静默失效（读者照着敲会找不到变量） |

第 ③ 条最容易漏——它不会报错，只会让文档「看起来对、实际跑不通」。
