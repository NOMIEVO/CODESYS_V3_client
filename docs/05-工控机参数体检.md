# 05 · 工控机参数体检（为什么同一客户端接工控机会慢）

> 适用：CODESYS Control RTE / Control Win 跑在 Windows 工控机上，客户端读变量明显慢于硬件 PLC。
> 结论先行：**网口速率不是主因**；网卡参数能拿回 0.5~1.5ms/操作，真正的大头在 Runtime 调度与符号配置。

---

## 1. 先量，不要猜

在**客户端电脑**上跑（只读，不写 PLC）：

```bash
node tools/probe-roundtrip.js <PLC_IP> <APP>
```

输出形状：

```
① TCP 连接（SYN→SYN-ACK，纯网络）　中位 1.1ms
② GetRoot 往返（1 请求）　　　　　中位 9.2ms
③ 分块阶梯（同一读取列表，改变响应块数）
   块数   数据量     耗时     每块增量
     1      0.0KB    14.2ms
     2      0.5KB    15.9ms     1.7ms/块
    92     42.4KB   984.2ms    10.8ms/块
```

判读：

| ① TCP 连接 | ② 协议往返 | 结论 |
|---|---|---|
| ≤1ms | ≤3ms | 正常，慢只可能来自数据量大 |
| ≤1ms | **8~10ms** | **Runtime 调度节拍**，网卡改了也没用 → 查任务周期 |
| 3~10ms | 略高于 ① | 网络/网卡/过滤驱动问题 → 按本文第 2、3 节处理 |
| 抖动大、有尖峰 | 同 | 丢包重传 / 网卡节能 / 杀软拦截 |

> 本协议每个动作都要等一次完整往返（每块 448B、每块都要 ACK），
> 所以 **一轮耗时 = (请求数 + 块数) × 单次往返**。单次往返 9ms 时 500 个操作就是 4.5s。

## 2. 网卡高级属性（收益 0.5~1.5ms/操作）

跑 `tools\win-nic-check.ps1` 自动逐项判定；也可手工在设备管理器 → 网卡 → 属性 → 高级里改。

| 参数 | 设为 | 原因 |
|---|---|---|
| 中断调整 Interrupt Moderation | **关闭** | 合并中断会让每次交互多等 0.5~2ms |
| 节能/绿色以太网、Gigabit Lite、Power Saving | **全关** | 空闲降速，突发时先唤醒 |
| 流控制 Flow Control | **关闭** | pause 帧导致整段停顿 |
| 大量传送减负 LSO v2 | **关闭** | 本协议全是小包，只有坏处 |
| 巨型帧 Jumbo | **关闭（1514）** | 帧 ≤516B，开了没收益还易不通 |
| 连接速度和双工 | **1.0 Gbps 全双工（固定）** | 自动协商可能落到 100M/半双工 |
| 接收/传送缓冲区 | **≥1024（建议 2048）** | 太小会丢帧重传 |
| 网络唤醒 WoL / ARP-NS 减负 / 优先级 VLAN | **关闭** | 生产无用 |
| 电源管理「允许关闭此设备省电」 | **取消勾选** | 空闲进低功耗态，首读变慢 |
| RSS | **保持开启** | 多核分担；仅绑单核时才关 |
| 硬件校验和 Offload | **保持开启** | 省 CPU，不加延迟 |

> 别把速率固定成 100M。稳是稳，但是白丢带宽、也没延迟收益。

## 3. 过滤驱动与虚拟网卡（收益 0.5~2ms）

```powershell
Get-NetAdapterBinding -Name '<网卡名>' | Where-Object {$_.Enabled}
```

路径上每个 NDIS 过滤驱动都会累加延迟。工控机上常见且通常不需要的：
Npcap（装了 Wireshark 就有，**最该关**）、TwinCAT RT-Ethernet Filter、PROFINET RT-Protocol、
SIMATIC ISO、各品牌 GigE Vision 驱动（Basler / HIK / OMRON）、VMware Bridge、杀软网络过滤。

```powershell
Disable-NetAdapterBinding -Name '<网卡名>' -ComponentID nmap_npcap    # 需管理员，网卡会闪断
```

同时确认面向 PLC 的是**物理网卡**（不是 `vEthernet`/`VMnet`），且该网段只绑一块网卡。

## 4. Windows 系统层

| 项 | 设为 |
|---|---|
| 电源计划 | 高性能 / 卓越性能 |
| 处理器最小状态 | 100% |
| PCIe 链接状态电源管理、USB 选择性暂停 | 关闭 |
| BIOS C-State / SpeedStep | 生产机建议关 C-State |
| TCP RSC | `netsh int tcp set global rsc=disabled` |
| TCP 自动调优 | `normal`（勿设 restricted） |
| 最大 SYN 重传 | `netsh int tcp set global maxsynretransmissions=2` |

链路质量用 `Get-NetAdapterStatistics` 看 Discarded / Packet Errors：
出现增长 → 双工不匹配或线材问题，软件改不了，换线换口。

## 4.5 「ping 要 1 秒」到底是怎么回事（三种情况，别混）

ping 的结果里，**`时间=1ms` 是 1 毫秒，不是 1 秒**。真正会让人以为"要 1 秒"的有三种情况：

| 现象 | 真实原因 | 怎么确认 |
|---|---|---|
| 看到 `时间=1ms` | 就是 1 毫秒。同一网段 0~1ms 属正常 | 换个 1400 字节大包再 ping，仍是 1ms → 带宽也不是瓶颈 |
| 每条回复**隔 1 秒**出现一次 | ping 默认每秒发一个包，那是**发包节奏**，不是延迟 | `time ping -n 6 <ip>`：整体约 5 秒（5 个间隔），而每包仍是 1ms |
| 第一条回复要等 2~6 秒 | **名称解析在拖**，不是网络慢 | 见下 |

### 名称解析拖慢（最容易被误判成"网络慢"）

`ping -a <ip>`（反查主机名）或 `ping <主机名>` 会先做 PTR/NetBIOS 查询。工业现场常见配置是：

```
以太网（连 PLC 的网段）  192.168.1.36   无网关、无 DNS     ← 隔离网段
WLAN                    192.168.3.212  DNS = 192.168.3.1
```

于是反查 `192.168.1.92` 会去问 192.168.3.1（它管不了 1.x 段），等超时再试 NetBIOS，
实测：**PTR 单次 2046ms，`ping -a` 整体 6.6 秒**，而回复本身始终是 1ms。

**影响与规避**：

- 用 **IP 直连**完全没有这个问题（本项目客户端就是直连 IP，不走名字解析）
- 用**主机名**连接的场合（CODESYS IDE、按名字写的采集程序、ping -a）每次新建连接都可能先等 2~6 秒，
  表现为"点一下就卡几秒"，很容易被误认为是 PLC 慢
- 想消除：给工控机网段配一台 DNS 或写 hosts，或干脆统一用 IP

### 真正 1 秒级的网络延迟长什么样

如果每包**确实是**几百毫秒到 1 秒，说明另有原因，按顺序查：

1. 双工不匹配（一端自适应成半双工）→ `Get-NetAdapterStatistics` 的 Packet Errors / Discarded 会增长
2. 网卡节能/EEE：空闲后首包要唤醒 → 连续 ping 时第一包慢、后面快
3. 经 Wi-Fi / VPN / 跨路由：ping 会稳定偏高，且抖动大
4. 对端 ICMP 限速：部分设备把 ICMP 压到 1 包/秒（但 TCP 通讯正常）——此时以
   `probe-roundtrip.js` 的 **TCP 握手中位**为准，它才是真实链路 RTT

## 5. 大头：Runtime 与符号配置

网卡全调完，单次往返通常只从 9ms 降到 7.5~8ms，全量仍是秒级。真正要动的是：

1. **Runtime 任务周期**：在 CODESYS 工程看 Task Configuration 各任务周期与 RTE 通讯设置。
   改完用 `probe-blockgap` 复测，**块间隔中位跟着下降才证明节拍来源就是它**。
2. **符号配置瘦身**：不要整条 `ARRAY[0..N] OF T_结构体` 地勾选，
   只勾 HMI 真正要显示的几个元素。大数组按 448B 一块计费：
   一个 33KB 的数组 = 77 块 ≈ 690ms（9ms/块），砍掉它比调十个网卡参数都值。

## 6. 脚本用法

```powershell
# 只读体检（不需要管理员）
powershell -ExecutionPolicy Bypass -File tools\win-nic-check.ps1 -PlcIp <PLC_IP>

# 先看会改什么，不写入
powershell -ExecutionPolicy Bypass -File tools\win-nic-check.ps1 -Apply -DryRun

# 实际应用（需管理员）：逐项打印 原值→新值，改不动的会写明原因
powershell -ExecutionPolicy Bypass -File tools\win-nic-check.ps1 -Apply

# 存档/对比
powershell -ExecutionPolicy Bypass -File tools\win-nic-check.ps1 -Json > nic.json
```

脚本会自动定位「能到达 PLC 的那块网卡」，兼容 Intel（英文属性名）与 Realtek（中文属性名），
认不出的项标 `[ -- ]` 而不是猜。

**改完必须复测**（同一台客户端、同一条命令），逐组改、逐组测，不要一次改十项——
否则无法判断哪一项有效。
