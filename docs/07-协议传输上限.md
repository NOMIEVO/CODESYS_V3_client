# 协议传输上限实测：「能不能不分包」

> 疑问来源：CODESYS IDE 内部的变量监控读写显得很快，而我们自己的客户端慢。
> 既然两者连的是同一台 PLC、走同一条块驱动/通道路径，那么差异是否在「分块」上？
> 能否让 PLC 一次回一大片、不必逐块 ACK？
>
> 结论：**不能。512 字节是 CODESYS PDU 协议写死的报文上限，分包不可避免。**
> 但「IDE 快」另有解释，而且这个解释对使用方式影响很大。下面是全部实测证据。

---

## 1. 结论表

| 假设 | 实测结果 | 结论 |
|---|---|---|
| PLC 可以回更大的块（不分包） | 改请求数据报长度码、发 11KB 单帧，PLC 一律不响应/超时 | ✗ 512B 硬上限 |
| 分块大小是客户端自选的 | 客户端申报的更大容量一律被拒 | ✗ 由协议与 PLC 固定 |
| 可以并发多个请求（流水线） | 在途 2 个请求 → `通道错误 8400` | ✗ 接收窗口 = 1 |
| 可以不逐块 ACK | 不回 ACK → 16 块后 `8400`，整次作废 | ✗ ACK 是硬门控 |
| 可以走 UDP 块驱动绕开 ACK | UDP 1740~1743 全部无响应 | ✗ 该 PLC 未开 UDP |
| 可以改 OpenChannel 的窗口/缓冲参数 | 任一字节改动 → 开通道超时（有整体校验） | ✗ 不可改 |
| 每个请求有 9ms 固定开销 | 1 块读 11.2ms、GetRoot 9.2ms、55 块/478ms | **单位是「每块 ≈8.7ms」，不是每请求** |

---

## 2. 512B 从哪来（外部证据 + 自测吻合）

独立安全研究（Kaspersky ICS CERT 对 CODESYS Runtime 的逆向）指出，
`CmpBlkDrvTcp` 的 `Receive()` 会校验块驱动头：

> 前 4 字节为 magic，**后 4 字节必须等于 520** —— 即 8 字节头 + **512 字节
> （CODESYS PDU 协议单个数据报的最大尺寸）**。

对应到实测，我们抓到的 PLC 回包恒定 508 字节数据报 / 516 字节帧：

```
55 块 · 491ms · 载荷 25820B        1 个 33KB 数组
长度分布：176B×1  508B×54
数据报头：c5 73 40 40 00 …           byte[3]=0x40 (=64)
```

`byte[3] ÷ 8` 正好是本帧容量（64×8 = 512）。把 `byte[3]` 改成 `0x80`（1024）
或 `0xFF`（2040）后，PLC 直接不再响应——因为它按声明长度等后续字节，等不到就超时。
这说明该字段是「本帧长度」，**不是可协商的接收能力**。

所以 PLC 自己已经在用最大值 508B/块，客户端没有任何提升空间。

---

## 3. 真正的成本单位：每块 8.7ms

这是最容易被误判的一点。数据：

| 场景 | 块数 | 总耗时 | 每块 |
|---|---|---|---|
| GetRoot（1 请求、无数据） | 1 | 9.2 ms | 9.2 |
| 读小数组 1.0KB | 3 | 34 ms | 11.3 |
| 读 33KB 数组 | 55 | 478 ms | **8.70** |
| 6 个列表（97 块） | 97 | 843 ms | **8.69** |
| 全量 596 符号（现场） | 432 | 4488 ms | 10.4（含列表尾块未填满） |

逐块到达间隔（33KB 数组，91 个样本）：

```
min 1.57 · p25 8.49 · 中位 8.89 · p75 8.99 · max 16.02 ms
84/91 落在 8.01~9.34 这一个桶里
```

**请求数几乎不占成本**：6 个请求只占 6×9 = 54ms，其余 790ms 全是「等块」。
所以「合并读取列表减少请求」这条路，收益上限只有几个百分点，而我们早知道
`PrepareRead` 载荷超 1 块还会触发 `8400`。

---

## 4. 那为什么 IDE 显得快？

因为 IDE 的每一次操作都是**一两个块**：

- 监控 10 个标量 → 1 个请求 → 1~2 块 → **约 10~20ms**，人眼完全无感
- 写一个值 → 1 个请求 → 1 块 → **约 9ms**，点下去就生效

**9ms 在交互上就是「瞬间」。** 但它乘上 400 块就是 3.5 秒。

### 现场可自证的实验

在 IDE 里对同一个人数组做监控，就能看到同样的耗时：

1. 打开监视窗口，加入 `GVL_AXIS.aAxisCtl`（33.3KB）并展开
2. 观察刷新：会明显顿一下（约 0.5s 一次），而不是像标量那样流畅
3. 对照：只监视 5 个标量时，几乎实时

如果符合上述现象，就证明「IDE 快」=「操作小」，而不是「路径不同」。

> 另一条可验证路径：IDE 的**跟踪/Trace** 采样是按任务周期在 PLC 内部完成的，
> 不经过逐块传输，所以看起来更"快"——但它采的是 PLC 内部缓冲，不是远程读变量。

## 5. 所以提速只有两条路

### 5.1 减少字节数（唯一线性有效）

块数 ≈ 字节数 ÷ 476。示例工程 44 个符号：

| 配置 | 块数 | 理论耗时 |
|---|---|---|
| 全部 596 符号（现状） | ~320 | **~2.8 s** |
| 去掉前 4 个大数组（省 82KB） | ~145 | ~1.3 s |
| 只留 HMI 实际用的标量 + 少量数组 | ~40 | ~0.35 s |

在 CODESYS 符号配置里**不要整条 `ARRAY[0..128] OF T_结构体` 地勾选**，
只勾要显示的元素。这条和「完整读」不冲突：完整读指「勾了的都要每轮刷新」，
而不是「把 PLC 里所有符号都勾上」。

### 5.2 提高每块速率（PLC 侧）

8.7ms/块 是 PLC 的调度节拍，客户端改不了。按
[`06-RTE实时性排查.md`](06-RTE实时性排查.md) 处理虚拟化与实时配置，
用 `probe-blockgap` 复测**间隔中位**是否下降：
从 8.7ms 降到 1ms，596 符号就从 2.8s 变成 0.35s。

## 6. 复现命令（全部只读）

```bash
# ① 分块上限：看 PLC 回包块长、试超大单帧
node tools/probe-blocksize.js dump
node tools/probe-blocksize.js txbig

# ② UDP 块驱动是否开放（若开放才可能绕开逐块 ACK）
node tools/probe-udp.js 192.168.1.92

# ③ 每块耗时与间隔分布
node tools/probe-blockgap.js 192.168.1.92 <APP> <大数组符号>

# ④ 全量一轮与两个成本系数
node tools/probe-baseline.js 192.168.1.92 <APP>
```

> 全部只读，不写入 PLC。跑之前先停验证台（PLC 只服务一条 TCP 连接）。

---

## 7. 一句话

**分包不是我们的选择，是 CODESYS PDU 的 512B 上限决定的**；
PLC 已经在用满上限（508B/块），并且每块都要一次 ACK 往返（8.7ms）。
IDE 感觉快，是因为它每次只碰一两块。
要让「看 596 个变量」变快，减字节（符号配置）比调协议有效得多。
