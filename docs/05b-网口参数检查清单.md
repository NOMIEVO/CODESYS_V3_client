# 工控机网口参数检查清单（面向 CODESYS RTE 通讯）

> 现场：`192.168.1.92` = Win10 工控机 + CODESYS Control RTE（原为 KSC-SA40 硬件 PLC）
> 现象：同一客户端、同一交换机，全量扫描 4.5s，SA40 上只要 75ms
> 本文只回答一件事：**网口/系统参数该改哪些、改成什么、改了能拿回多少**

---

## 0. 先看结论：网口速率不是主因

我在这台工控机上把一次往返拆成三段实测：

| 测量项 | 结果 | 说明 |
|---|---|---|
| TCP 握手（SYN→SYN-ACK） | **1.1 ms** | 由 Windows 内核 TCP 栈处理，**经过网卡驱动和中断** |
| 协议单请求（GetRoot，1 块） | **9.2 ms** | 进入 CODESYS Runtime 应用层 |
| 每多一块（448B 续块） | **8.7~9.0 ms** | 也是 8.5/9.0 交替，高度量化 |
| 客户端「收到块→回 ACK」 | **0.006 ms** | 客户端无嫌疑 |

三条推论：

1. **带宽完全不是瓶颈**。该协议帧最大 516B，全量 150KB 数据摊到 4.5s，平均只有 **约 33 KB/s（0.27 Mbps）**。
   千兆口用不到 0.03%，百兆口也用不到 0.3%。**把速率从 100M 提到 1G 不会让它变快。**
2. **网卡路径本身也不慢**。TCP 握手 1.1ms 已经包含了网卡中断、驱动、协议栈——这部分是健康的。
   健康值应 ≤0.5~1ms；现在 1.1ms，勉强合格，可优化空间约 0.5ms。
3. **~8ms 花在 Runtime 应用层**。8.5/9.0 交替、96% 落在窄区间，这是调度节拍的形态，
   不是网络抖动，也不是丢包（无错包、无重传）。

**所以：网口参数值得做（能拿回 0.5~1.5ms/操作，约 10~15%），但决定 4.5s 的是 Runtime 的任务周期与符号配置。**
按本文把「不该有的延迟」清掉，再去查 Runtime。

## 1. 网卡高级属性（收益：单包 RTT 可降 7 倍；协议总耗时基本不变）

设备管理器 → 网络适配器 → 右键网卡 → 属性 → **高级** 选项卡。
或直接跑 `tools\win-nic-check.ps1`，它会按下面的表逐项判定。

| # | 参数（常见中/英名） | 设为 | 为什么 | 实测效果 |
|---|---|---|---|---|
| 1 | **节能以太网 / 绿色以太网 / Gigabit Lite / Power Saving Mode** (EEE) | **关闭** | 空闲降速、PHY 休眠，收包要先唤醒 | **最关键：RTT 0.93ms → 0.13ms（7 倍）**，见 §4.6 |
| 2 | **电源管理**「允许计算机关闭此设备以省电」 | **取消勾选** | 同上，空闲进低功耗态 | 同上，属同一类 |
| 3 | **中断调整** Interrupt Moderation | 关闭（次要） | 合并中断成批上报 | **实测与"空闲后变慢"无关**（关掉仍 0.93ms），只对持续高速小包有轻微帮助 |
| 4 | **流控制** Flow Control | **关闭** | pause 帧会让发送方整段停顿；本协议突发小包多 | 偶发几十 ms 停顿 |
| 5 | **大量传送减负 LSO v2** | **关闭** | 大包分片交给网卡，本协议全是小包，只有坏处 | 少量不确定延迟 |
| 6 | **巨型帧** Jumbo Frame | **关闭（1514）** | 帧只有 516B，开巨型帧毫无收益；且要求全链路一致 | 不一致时直接不通 |
| 7 | **连接速度和双工模式** Speed & Duplex | **1.0 Gbps 全双工（固定）** | 自动协商在部分交换机上会落到 100M 或半双工 | 半双工 → 冲突、丢包、重传 |
| 8 | **接收/传送缓冲区** Receive/Transmit Buffers | **≥1024（建议 2048）** | 缓冲区太小会丢帧并触发重传 | 突发时丢包重传 |
| 9 | **网络唤醒** WoL / Wake on Magic Packet / S5WakeOnLan | **关闭** | 生产环境无用，保持待机逻辑活跃 | 属节能类，一并关 |
| 10 | **ARP/NS 减负** | **关闭** | 交给网卡代答，个别驱动引入额外处理 | 轻微 |
| 11 | **优先级和 VLAN 标记** Priority & VLAN | **关闭**（不用 VLAN 时） | 每包少一层处理 | 轻微 |
| 12 | **RSS 接收端调整** | **保持开启** | 多核分担中断；只有「把 RTE 绑到单核」时才关 | 关掉会挤单核 |
| 13 | 硬件校验和（IPv4/IPv6 TCP/UDP Checksum Offload） | **开启（推荐）** | 省 CPU，不增加延迟；与 LSO 不同 | 只是费 CPU |

> ⚠️ **不要**为了「稳定」把速率固定成 100M 全双工。那会让链路协商变稳，但带宽降到 1/10，
> 而本协议虽然带宽占用很低，100M 下的突发吸收能力也差，且没有任何延迟收益。

## 2. 过滤驱动 / 虚拟网卡（收益 0.5~2ms，风险低）

每个绑在网卡上的 NDIS 过滤驱动都在**收发路径**上，逐层加时间。工控机上常见且**通常不需要**的：

| 驱动 | 什么时候可以禁用 |
|---|---|
| Npcap Packet Driver（装了 Wireshark 就有） | 抓包结束后禁用，**这是最该关的一个** |
| TwinCAT RT-Ethernet Filter | 该机器不做 TwinCAT 主站时 |
| PROFINET IO RT-Protocol / PROFINET IO protocol（DCP/LLDP/RSI） | 只做 CODESYS V3 通讯时 |
| SIMATIC Industrial Ethernet (ISO) | 同上 |
| pylon GigE Vision / OMRON SENTECH / HIK GiGEVision Image Filter | 不接对应品牌工业相机时 |
| VMware Bridge Protocol | 物理网卡上不需要（VMware 自己会建虚拟网卡） |
| 杀毒/EDR 的网络过滤（NDIS 6 LWF） | 把 CODESYS 目录与 11740 端口加白；必要时换「仅文件扫描」档 |

查看与禁用：

```powershell
# 看这块网卡上绑了哪些（Enabled=True 的就是在路径上的）
Get-NetAdapterBinding -Name '以太网' | Where-Object {$_.Enabled}

# 禁用其中某一项（要管理员，改完网卡会闪断一下）
Disable-NetAdapterBinding -Name '以太网' -ComponentID nmap_npcap
```

另外确认：**面向 PLC 的那块必须是物理网卡**，不能是 `vEthernet` / `VMnet`。
看名字或 `Get-NetAdapter | Select Name,Virtual,Status`。

## 3. Windows 系统层（收益 0~2ms，主要防抖动）

| 项 | 设为 | 检查命令 |
|---|---|---|
| 电源计划 | **高性能 / 卓越性能** | `powercfg /getactivescheme` |
| 处理器最小状态 | **100%**（避免降频/C-state 抖动） | `powercfg /setacvalueindex SCHEME_CURRENT SUB_PROCESSOR PROCTHROTTLEMIN 100` |
| PCIe 链接状态电源管理 | **关闭** | 电源选项 → 高级 → PCI Express → 链接状态电源管理 → 关闭 |
| 硬盘/USB 选择性暂停 | 关闭（USB 网卡必须关） | 电源选项 → 高级 |
| BIOS C-State / SpeedStep / EIST | 生产机建议关 C-State | BIOS 设置 |
| TCP 接收段合并 RSC | **disabled** | `netsh int tcp set global rsc=disabled` |
| TCP 自动调优 | **normal**（别设 restricted） | `netsh int tcp show global` |
| 最大 SYN 重传 | 2（加快故障识别，不影响正常速度） | `netsh int tcp set global maxsynretransmissions=2` |
| Windows 更新 / 计划任务 / 杀软扫描 | 生产时段暂停 | 任务计划程序 |

> **关于「提高定时器精度」**：`timeBeginPeriod(1)` 能减少调度抖动，但由进程自己调用才有效。
> CODESYS Runtime 通常会自己设置；不要去装第三方「定时器优化」工具，容易和其它实时组件冲突。

## 4. 链路与交换机（用来排除「不是网口设置的问题」）

| 检查 | 合格值 | 不合格说明 |
|---|---|---|
| `Get-NetAdapterStatistics` 的 Discarded | 接近 0（少量历史计数可接受） | 持续增长 → 双工不匹配 / 线材老化 / 缓冲区太小 |
| Packet Errors | **0** | 有任何增长 → 换线换口，软件改不了 |
| 实际 LinkSpeed | 1 Gbps | 只有 100 Mbps → 网线只有 4 芯或交换机口是百兆 |
| 中间设备 | 直连同一交换机（不经路由器/VPN） | 经三层设备会引入排队与突发丢包 |
| 同网段多 IP | 只保留一块网卡有该网段地址 | 两条路径都能到 PLC → 偶发走错卡超时 |

## 4.5「ping 要 1 秒」到底是怎么回事（三种情况，别混）

ping 输出里 **`时间=1ms` 是 1 毫秒，不是 1 秒**。真正会让人以为"要 1 秒"的只有三种：

| 现象 | 真实原因 | 怎么确认 |
|---|---|---|
| 看到 `时间=1ms` | 就是 1 毫秒。同一网段 0~1ms 属正常 | 换 1400 字节大包再 ping，仍是 1ms → 带宽也不是瓶颈 |
| 每条回复**隔 1 秒**出现 | ping 默认每秒发一个包，那是**发包节奏**，不是延迟 | `time ping -n 6 <ip>`：整体约 5 秒（5 个间隔），每包仍 1ms |
| 第一条回复要等 2~6 秒 | **名称解析在拖**，不是网络慢 | 见下 |

### 名称解析拖慢（最容易被误判成"网络慢"）

`ping -a <ip>`（反查主机名）或 `ping <主机名>` 会先做 PTR/NetBIOS 查询。现场实测的网卡配置：

```
以太网（连 PLC 的网段）  192.168.1.36   无网关、无 DNS      ← 隔离网段
WLAN                    192.168.3.212  网关+DNS 192.168.3.1  ← 唯一的 DNS
```

反查 `192.168.1.92` 会去问 192.168.3.1（它管不了 1.x 段），超时后再试 NetBIOS：

```
PTR 单次查询       2046 ms   （返回空）
ping -n 1 -a 整体  6.6 秒    （而回复本身仍是 1ms）
```

**影响与规避**：

- **IP 直连完全没有这个问题**（本项目客户端就是直连 IP，不走名字解析）
- 用**主机名**连接的场合（CODESYS IDE、按名字写的采集程序、`ping -a`）每次新建连接都可能先等 2~6 秒，
  表现为"点一下就卡几秒"，很容易误认为是 PLC 慢
- 想消除：给该网段配 DNS 或写 hosts，或统一用 IP

### 真正 1 秒级的网络延迟长什么样

若每包**确实是**几百毫秒到 1 秒，按顺序查：

1. 双工不匹配（一端自适应成半双工）→ `Get-NetAdapterStatistics` 的 Packet Errors / Discarded 会增长
2. 网卡节能/EEE：空闲后首包要唤醒 → 连 ping 时第一包慢、后面快
3. 经 Wi-Fi / VPN / 跨路由：稳定偏高且抖动大
4. 对端 ICMP 限速：部分设备把 ICMP 压到 1 包/秒（TCP 通讯仍正常）——
   此时以 TCP 通讯是否正常为准

## 4.6 实测：0.93ms 的元凶是「节能」，不是中断节流

用系统内置 `pktmon` 取帧时间戳（`Windows ping` 只显示整数毫秒，看不出 0.13 与 0.93 的差别），
同一台机器做了四组对照，全部是「网卡重启后先测一次，空闲 60~80 秒后再测一次」：

| 节能项 | 中断节流 | 刚重启 | 空闲 60~80s 后 | 结论 |
|---|---|---|---|---|
| 开 | 开 | — | **0.934 ms** | 基线 |
| 开 | **关** | 0.145 ms | **0.935 ms** | 关节流**无效**，空闲后又变慢 |
| **关** | 关 | 0.125 ms | **0.127 ms** | 有效，稳定 |
| **关** | **开** | 0.118 ms | **0.131 ms** | 有效，且不必关节流 |

**结论：节能机制才是元凶**（EEE / 绿色以太网 / Power Saving Mode / 网络唤醒 / 设备省电），
关掉后 **0.93ms → 0.13ms，约 7 倍**；与中断节流无关。

机制：网卡空闲后进低功耗态，每个收到的包都要先把 PHY/链路唤醒，多付约 0.8ms。
这也解释了「刚开机/刚插网线时很快，过一会就越用越慢」的现象。

### 关掉后的效果边界（重要，别期待错方向）

| 指标 | 节能开 | 节能关 | 说明 |
|---|---|---|---|
| 单包 RTT | 0.934 ms | **0.131 ms** | 7 倍，交互响应明显变快 |
| 协议每块中位 | 8.89 ms | 8.58 ms | **基本不变**：由 PLC 节拍门控 |
| 协议 p95 | 14.93 ms | **9.07 ms** | 尾部抖动明显收窄 |
| 协议 max | 19.49 ms | **13.99 ms** | 同上 |

也就是说：**它让「点一下就有反应」变快（IDE、单变量读写），但不会让「读 500 个变量」变快**——
后者受 PLC 每块 8.6ms 的节拍限制（见 [`07-协议传输上限.md`](07-协议传输上限.md)）。

### 一条命令验证

```powershell
# 需管理员；取真实链路 RTT，并自动对照说明
powershell -ExecutionPolicy Bypass -File tools\probe-rtt.ps1 -Target 192.168.1.92

# 先空闲 70 秒再测，专门复现「越用越慢」
powershell -ExecutionPolicy Bypass -File tools\probe-rtt.ps1 -Target 192.168.1.92 -IdleSeconds 70
```

判据：**中位 <0.30ms 正常**。若在 0.5~1.5ms，先查节能项。

## 5. 最后才是大头：Runtime 与符号配置

网口全部按上面调完，每操作大概从 8.96ms 降到 7.5~8ms，全量 4.5s → 约 4.0s。**该做的都做了，仍然是「几秒级」。**

要真正降下来只有两条：

**① Runtime 任务周期**（决定那 ~8ms 的节拍）
在 CODESYS 工程里看 Task Configuration 各任务的周期；再看 RTE 的通讯/系统作业设置。
改了以后用 `probe-blockgap` 复测——**块间隔中位跟着变，才证明节拍来源就是它**。

**② 符号配置瘦身**（决定操作数，收益最大）
这台工控机 示例规模的符号表，前 4 个数组就占 38%：

| 符号 | 大小 | 块 | 折算 |
|---|---|---|---|
| `<大数组>` | 33.3 KB | 77 | 690 ms |
| `<大数组>` | 23.6 KB | 54 | 484 ms |
| `<大数组>` | 13.0 KB | 30 | 269 ms |
| `<大数组>` | 12.1 KB | 28 | 251 ms |

HMI 不需要整条 `ARRAY[0..128] OF T_AXIS_CONTROL`，只勾要显示的几支轴即可。这一步能省 1~1.7s，且不损失任何「完整读」的要求——只是把「PLC 侧暴露的符号」缩小到实际需要的范围。

## 6. 操作流程（改一项，测一次）

```
① 先测基线（在客户端电脑，只读）
   node tools/probe-roundtrip.js  <PLC_IP> <APP>
   记下：TCP 握手 = ___ms    协议往返 = ___ms    每块 = ___ms

② 在工控机上体检
   powershell -ExecutionPolicy Bypass -File tools\win-nic-check.ps1 -PlcIp <PLC_IP>
   记下「需要处理」的项数

③ 逐组改，每组改完测一次（别一次全改，否则不知道哪项有效）
   第 1 组：中断调整 + 三个节能项           → 期望 TCP 握手降到 ≤0.5ms
   第 2 组：过滤驱动（先关 Npcap）           → 期望协议往返降 0.5~1ms
   第 3 组：速率固定 1G + 缓冲区 2048 + 取消省电 → 期望抖动变小
   第 4 组：电源计划高性能 + 关 C-state      → 期望块间隔更稳定

④ 每组都用同一条命令复测，把数字填回去对比

⑤ 若四组做完协议往返仍 ≈8~9ms：
   说明瓶颈是 Runtime 节拍，请转 docs/06-RTE实时性排查.md
```

> 改网卡属性后，**断开/重连网线**（或 `Restart-NetAdapter`）才生效；改电源计划需要重启更彻底。

## 7. 脚本说明

`tools/win-nic-check.ps1`

| 用法 | 作用 |
|---|---|
| `-PlcIp 192.168.1.92` | 自动找出「能到达 PLC 的那块网卡」并只检查它 |
| 无参数 | 只读体检，输出 `[ OK ] / [!!] / [!!!]` 分级的清单与原因 |
| `-Apply -DryRun` | 列出「将会改什么」，不写入 |
| `-Apply` | 实际写入建议值（需管理员），逐项打印 原值→新值，失败的写明原因 |
| `-Json` | 输出 JSON，便于两台机器对比或存档 |
| `-Adapter '以太网'` | 手动指定网卡（自动定位不准时用） |

脚本兼容 Intel（英文属性名）与 Realtek（中文属性名，如「中断调整」「节能以太网络」），
认不出的项会标 `[ -- ]` 而不是瞎猜。
